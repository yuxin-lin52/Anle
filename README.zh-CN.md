<h1 align="center">Anle</h1>

<p align="center"><a href="README.md">English</a> | 中文</p>

Anle 是一门 AOT 编译语言。内存由编译器管理：回收点从程序的块结构算出，运行时没有垃圾回收器、没有停顿、没有逐对象计数。

## 设计动机

Anle 建立在一个分工之上：**写得简单，实现得复杂。**

每门语言都要回答一个问题：内存谁负责？手动管理把正确性交给程序员；运行时管理省掉了这项工作，但带来额外负担和运行时卡顿；编译器检查的所有权保证了正确性，代价是程序员必须学会并满足一套规则。

Anle 三种取舍都不取。程序按块结构化，值长在声明它的块里，一切跨块数据流动都走显式通道。在此结构下，编译器算出每个值的寿命与回收点。程序员写块、声明数据流向，其余由编译器完成。

整个语言都遵循同一个分工。语法小而规整。直接内存访问与显式提前回收（`kill`）只存在于 `unsafe` 块内。Anle 没有手动内存分配。预期是直接编译成由后端手动管理内存的形态；因实现难度，目前生成的代码里内嵌了一个运行时分配器——这是已知偏差，后续会修缮。Anle 另提供内联汇编与 C ABI 互操作，供需要自备环境的情形使用。

## 语言概览

```anle
#: 主块 b
    add val "和" int = 0
    add val "i" int = 1
    while call val "i" <= 100:
        val "和" = call val "和" + call val "i"
        val "i" = call val "i" + 1
    ;
    print(call val "和")
#: 主块 d
```

输出 `5050`。这个例子里能看到的规则：

- 所有代码写在块里。块用 `#: 名 b`（born）开、`#: 名 d`（death）关。块是平的，不嵌套。
- 名字用 `add` 创建，用 `val "名" =` 改值（`add` 不重复出现）。
- 读值写 `call val "名"`。没有裸名：每次读取都声明类别，每次跨块引用都写明来源。
- 没有隐式转换。`int` 与 `float` 不显式转换不混算。
- 条件必须是真假值——`if 5:` 是编译错误。
- 下标从 1 起，与含两端的范围符一致（`for i in 1~5` 覆盖 1 到 5）。
- 控制流体用独占一行的 `;` 收束。缩进纯属装饰、不可能改变语义；`;` 不配对是响亮的解析错误。Anle 的编辑器扩展内置自动格式化，会保持缩进一致。

## 内存模型

- 内存按块实例分配。块的地皮回收时，其中一切随之回收；回收是每段 O(1)，不是逐对象。
- 回收点在编译期由块引用图定死。运行时没有 GC 线程、没有全局停顿、没有引用计数。
- 跨块数据有两种显式形态：**引用槽**（`call #:块 val "名"`——读到最新值，写入直达）与**深拷**（`take #:块 val "名"`——当时的值归调用者所有）。
- 引用环不泄漏，因为根本不存在逐对象回收。

这套模型给所有程序员同一个简单默认：把代码写进块里，内存自己管理好——初学者可以把整个程序写在一个块里，零内存负担。块怎么划不影响正确性，只影响内存占用。对内存或性能敏感的项目，高阶开发者可以自行调优：一个步骤一个块，配合 `unsafe` 里的 `kill`，把内存峰值压低。

## 下载

[最新 release](https://github.com/yuxin-lin52/Anle/releases) 附带 Windows x64 的预构建二进制（仅 C 后端）。它仍需要一个 C 工具链：`PATH` 里有 `clang`，或用 `ANLE_CC` 指向一个。预构建二进制不含 LLVM 后端，需要它请从源码构建（见下）。

## 构建

编译器源码在 [`compiler/`](compiler)，是九个 crate 的 Rust 工作区。

```
cd compiler
cargo build --release -p anlec --no-default-features --features backend   # 仅 C 后端，不需要 LLVM
cargo build --release -p anlec                                   # 两条后端，需要 LLVM 18.1
```

C 后端把中间表示翻成 C 源码文本，交给 `clang`（路径取 `ANLE_CC`，未设则用 `PATH` 里的 `clang`）。LLVM 后端链 `LLVM-C.dll`，故 `LLVM_SYS_181_PREFIX` 需指向 LLVM 18.1 安装目录。本仓库不随附 LLVM，请从上游发布页获取：<https://github.com/llvm/llvm-project/releases>。

```
./target/release/anlec build demos/zh/物理引擎/物理引擎
```

## 实现状态

- 编译器由 Rust 实现，源码随仓提供。自举处于早期：自举前端的词法器已完成，与宿主实现通过逐 token 对拍。
- 两条后端已实现：**C** 与 **LLVM**；两者都经 clang 编译，同一份源码经两条后端编译，程序输出逐字节一致。
- 生成的代码比手写 C 慢。已定位的开销在两处：逐语句的源码位置记账、句柄间接寻址。
- 已知缺陷：泛型函数的形参解析不完整；部分诊断文案与实际原因不符。
- 语法**未冻结**。破坏性变更随时可能；针对本语言写的代码需要跟着更新。
- 标准库由约 40 个内置函数构成。

## 验证

项目的验收判据是程序行为，不是单元测试数量。例：[demos/zh/物理引擎/](demos/zh/%E7%89%A9%E7%90%86%E5%BC%95%E6%93%8E/%E7%89%A9%E7%90%86%E5%BC%95%E6%93%8E.an) 中的物理引擎演示——

- 400 粒子、400 模拟步、约 3200 万对碰撞检测。
- 程序在跑完后自检四条不变量（弹性交换、动量守恒、墙反弹、界内约束），实录输出：

```
对撞交换 通过
动量守恒 通过
墙反弹 通过
界内约束 通过
基准完成 碰次 7343
```

- 碰撞次数 7343 与 C、Rust 参照实现完全一致。
- 两条编译后端产出逐字节一致的输出；连续三次运行结果相同。

## 诊断格式

诊断带四段：发生了什么、源码原文、编译器预期、改法。当前以中文输出；本地化在路线图上。真实样例：

```
[E202] 位于 例.an 第 2 行第 1 列的「赋值」发生错误，
源码为：add val "v" float = 0 - 5，
错误为：「v」声明是 float，右边是 int，
编译器预期为：右边的值应当是 float 型（左边声明说了算）。
改法：改成 float 的值，或把声明改成 int。
```
